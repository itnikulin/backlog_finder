# Backlog Finder

Советник по продуктовому бэклогу для Kilo Code с закрытым контуром обработки данных. Агент получает актуальный бэклог Kaiten через локальный MCP-сервер в режиме «только чтение» и отправляет данные для анализа только в отдельно настроенную внутреннюю ИИ-модель.

Подробная инструкция по установке и настройке: [`docs/SETUP_RU.md`](docs/SETUP_RU.md).

## Контур данных

Система использует два независимых ключа:

- `KAITEN_API_TOKEN` читает только локальный MCP-процесс и использует исключительно для обращения к корпоративному домену Kaiten;
- `INTERNAL_AI_API_KEY` читает Kilo Code и использует исключительно для обращения к внутренней модели, настроенной в локальном `kilo.jsonc`.

Не вставляйте ключи в запросы агенту, исходный код, общедоступные настройки GitHub или журналы работы.

## Быстрая настройка

Понадобятся Node.js 20 или новее, Kilo Code, сетевой доступ к Kaiten и внутреннему API ИИ-модели.

1. Установите зависимости:

   ```bash
   npm install
   npm run init:context
   ```

2. Передайте ключи через окружение терминала, из которого запускается Kilo Code:

   ```bash
   export KAITEN_BASE_URL="https://your-company.kaiten.ru"
   export KAITEN_ALLOWED_BOARD_IDS="123,456"
   export KAITEN_API_TOKEN="..."
   export INTERNAL_AI_API_KEY="..."
   ```

   Укажите только согласованные ID досок. Без `KAITEN_ALLOWED_BOARD_IDS` сервер не запускается. Предпочтительно использовать корпоративное хранилище секретов. `.env` и `.env.*` (кроме публичного `.env.example`) исключены из Git, но проект не загружает их автоматически.

3. Объедините настройки из `config/kilo.global.example.jsonc` с доверенной глобальной конфигурацией `~/.config/kilo/kilo.jsonc`. Замените:

   - `baseURL` внутренней ИИ-модели;
   - `replace-model-id` в выбранной модели и конфигурации провайдера;
   - `/ABSOLUTE/PATH/TO/backlog_finder` на абсолютный путь к клонированному репозиторию;
   - `REQUIRED_CONTEXT_TOKENS` и `REQUIRED_OUTPUT_TOKENS` на подтверждённые AI-командой положительные числа **без кавычек**.

   Шаблон намеренно не является готовым конфигом: заглушки лимитов не проходят схему Kilo. Подтвердите поддержку tool calling, установите `tool_call: true` и проверьте вызов инструмента на тестовых данных. Не включайте `reasoning` без подтверждения поддержки. После настройки модели и списка досок установите `mcp.kaiten.enabled: true`.

   Оставьте ключи в виде ссылок `{env:...}`. Kilo не подставляет секреты из недоверенной проектной конфигурации.

4. При необходимости скопируйте `kilo.project.example.jsonc` в `kilo.jsonc`, чтобы подключить проектные инструкции и разрешения. Этот файл не содержит секретов.

5. Выйдите из Kilo Gateway. Отключите автодополнение либо настройте его на тот же внутренний провайдер.

6. Заполните созданный приватный `context/product-passport.md`: результаты, ограничения, пространства и доски Kaiten, соответствие пользовательских полей. Папка `context/` не отслеживается Git; публичные пустые шаблоны находятся в `templates/context/`. Повторный `npm run init:context` сохраняет существующие документы.

7. Откройте репозиторий в Kilo Code и выберите агента `backlog-advisor`.

## Первые запросы

- `Покажи пространства с разрешёнными досками Kaiten. Если список усечён, продолжи загрузку.`
- `/prioritize-backlog для доски 123. Исключи завершённые карточки.`
- `/build-roadmap на ближайшие шесть месяцев в формате Now / Next / Later.`
- `/update-product-context В этом квартале удержание пользователей важнее привлечения.`

## Режим советника

MCP-сервер намеренно предоставляет только инструменты чтения. Если пользователь просит изменить Kaiten, агент формирует предлагаемый пакет изменений, но не может его применить.

Инструменты записи следует добавлять только после проверки качества рекомендаций и согласования правил подтверждения и аудита.

## Граница доступа и приватный контекст

- `list_cards` требует один разрешённый `board_id`; запрос без доски или с посторонним ID отклоняется до обращения к API. Для нескольких досок нужны отдельные вызовы.
- Каждое чтение карточки проверяет её текущую доску. Комментарии и история проверяются до и после загрузки. История посторонних досок скрывается.
- Пространства возвращаются только с разрешёнными досками и минимальными метаданными, без вложенных карточек.
- Это ограничение выдачи данных агенту, а не замена прав Kaiten: для проверки принадлежности сервер получает карточку по ID; список пространств тоже фильтруется локально. Ограничьте доступ технической учётной записи на стороне Kaiten. Текст разрешённых карточек/комментариев может содержать упоминания других проектов; сервер не является системой автоматического удаления таких упоминаний.
- Рабочий контекст храните локально или в одобренном приватном хранилище. Не используйте `git add -f` для `context/`, `.env*` и выгрузок.
- При обновлении старой версии сначала сохраните заполненные `context/*.md` вне репозитория, затем обновите код, выполните `npm run init:context` и восстановите рабочие документы. Удаление файлов из текущей версии Git **не удаляет историю**: если реальные данные уже публиковались, отдельно ограничьте доступ и проведите очистку истории; утекшие ключи отзовите.

## Инструменты MCP

- `list_spaces`;
- `get_space`;
- `list_cards`;
- `get_card`;
- `get_card_comments`;
- `get_card_location_history`.

Инструмент получения списка карточек использует `GET /api/latest/cards`, поддерживает пагинацию и возвращает компактные ответы. За один вызов он может получить до 25 страниц, но агенту предписано ограничивать область анализа и запрашивать подробности только для выбранных карточек.

`list_spaces` принимает `limit` (1–100), `offset`, `max_pages` (1–25) и возвращает `spaces`, `truncated`, `next_offset`. Продолжайте с `next_offset`, пока `truncated: true`, даже если отфильтрованный `spaces` пуст. Смещение считается по исходному ответу API, а не по числу разрешённых пространств.
